# Skill Creation Guide

A skill in DevManager is a **markdown instruction template** stored in the database and synced to projects as `.claude/skills/<name>/SKILL.md` for Claude Code to follow during sessions.

This guide teaches you how to write effective skills that Claude Code will understand and follow correctly.

---

## CRITICAL RULE

- **NEVER** create skills without valid YAML frontmatter (name, description, user-invocable)
- **ALWAYS** test skills in a single project before syncing to all projects
- **NEVER** include YAML frontmatter in the `content` field when creating/updating via API (it's auto-generated)
- **ALWAYS** use lowercase-with-hyphens for skill names (e.g. `python-best-practices`, not `Python Best Practices`)
- **ALWAYS** include bilingual keywords (PT + EN) in descriptions and trigger examples for user-invocable skills

---

## Skill Anatomy

### YAML Frontmatter (auto-generated by DevManager)

```yaml
---
name: my-skill-name
description: "What this skill does and when to use it"
user-invocable: true  # or false
allowed-tools:        # optional, only for automation skills
  - Bash
  - Edit
  - Write
---
```

**Fields:**
- `name`: lowercase-with-hyphens, max 64 chars (auto-filled from DB)
- `description`: Clear explanation of when Claude Code should use this skill (auto-filled from DB)
- `user-invocable`: 
  - `true` = automation skill (user triggers with keywords like "deploy", "test", "commit")
  - `false` = background knowledge (Claude Code reads but doesn't execute as a task)
- `allowed-tools`: (optional) restrict which tools Claude Code can use during execution

### Content Structure

```markdown
# Skill Title

Brief intro explaining what this skill does.

---

## CRITICAL RULE (if applicable)

- **NEVER** do X
- **ALWAYS** do Y
- Use this section for safety rules, production warnings, etc.

---

## Instructions

1. Step-by-step instructions
2. Use numbered lists for sequences
3. Use bullet points for guidelines

## Examples

\`\`\`bash
# Show concrete examples
make build
./devmanager &
\`\`\`

## Success Criteria (for automation skills)

- Output shows "✓ Build successful"
- Service responds on expected port
- No errors in logs

## Common Mistakes to Avoid

- Don't do X because Y
- Always check Z before running
```

## Skill Patterns

### Pattern 1: Automation Task (user-invocable: true)

**Use when:** User wants to trigger a specific workflow (deploy, test, commit, etc.)

**Example: Deploy Skill**

```yaml
---
name: deploy
description: "Deploy the application to production (.run directory, port 8081). Use when user says: deploy, fazer deploy, atualizar o serviço, subir o serviço, restart da produção, update production."
user-invocable: true
allowed-tools:
  - Bash
  - Read
---

# Deploy to Production

Deploy the DevManager application to the .run directory on port 8081.

---

## CRITICAL RULE

- **NEVER** deploy without running tests first
- **ALWAYS** create a git tag before deploying
- **NEVER** kill the production process (port 8081) unless explicitly deploying

---

## Instructions

1. Run tests: `make test`
2. Build binary: `make build`
3. Stop old production process: `pkill -f "devmanager -port 8081"`
4. Copy binary to .run: `cp build/devmanager .run/`
5. Start production: `cd .run && nohup ./devmanager -port 8081 &`
6. Verify service is up: `curl http://localhost:8081/health`

## Success Criteria

- Tests pass before deploy
- Binary copied to .run/
- Service responds on port 8081
- No errors in nohup.out

## Common Mistakes to Avoid

- Don't deploy without testing
- Don't forget to update .run/ directory
- Don't use port 8080 for production
```

---

### Pattern 2: Background Knowledge (user-invocable: false)

**Use when:** You want Claude Code to always follow certain guidelines/rules without explicit user trigger.

**Example: Python Best Practices**

```yaml
---
name: python-best-practices
description: "General Python coding standards. Claude Code should follow these automatically when writing Python code."
user-invocable: false
---

# Python Best Practices

Follow these guidelines when writing or editing Python code in this project.

---

## Code Style

- Use type hints in all function signatures
- Prefer `pathlib.Path` over `os.path`
- Use f-strings instead of `.format()` or `%`
- Max line length: 100 characters
- Use dataclasses for simple data containers

## Error Handling

- Catch specific exceptions, never bare `except:`
- Use `logging` module, not `print()` for debugging
- Validate inputs at function boundaries

## Testing

- Write unit tests for all public functions
- Use pytest fixtures for common setup
- Aim for >80% code coverage

## Common Mistakes to Avoid

- Don't use mutable default arguments
- Don't ignore type checker warnings
- Don't commit code with `print()` statements
```

### Pattern 3: Git Workflow (user-invocable: true)

**Example: Smart Commit**

```yaml
---
name: commit
description: "Create a git commit with a well-crafted message. Use when user says: commit, fazer commit, salvar alterações, commit changes, save changes."
user-invocable: true
allowed-tools:
  - Bash
  - Read
---

# Git Commit with Smart Message

Create a commit with a conventional commit message based on staged changes.

---

## Instructions

1. Check git status: `git status`
2. If no staged changes, ask user what to stage
3. Review diff: `git diff --staged`
4. Generate commit message following Conventional Commits format:
   - `feat:` for new features
   - `fix:` for bug fixes
   - `docs:` for documentation
   - `refactor:` for code refactoring
   - `test:` for tests
   - `chore:` for build/config changes
5. Create commit: `git commit -m "type: description"`

## Success Criteria

- Commit message follows Conventional Commits format
- Message is concise and descriptive
- User approves message before committing

## Common Mistakes to Avoid

- Don't commit without reviewing staged changes
- Don't use vague messages like "fix stuff"
- Don't auto-commit without user confirmation
```

## Bilingual Support (PT + EN)

For user-invocable skills, include both Portuguese and English keywords in the description so users can trigger the skill in either language.

**Example:**
```yaml
description: "Run tests using Playwright. Use when user says: test, testar, rodar testes, run tests, check the UI, verificar interface."
```

## Success Criteria for a Well-Written Skill

A skill is well-written when:

- ✅ It loads without errors in Claude Code session
- ✅ Description clearly indicates when to use it (with PT+EN keywords for user-invocable skills)
- ✅ Critical rules are highlighted and followed during execution
- ✅ Examples are accurate and tested in the actual project
- ✅ Success criteria are measurable and clear
- ✅ Common mistakes are documented and avoided
- ✅ `allowed-tools` restricts Claude Code to safe tools (for automation skills)

---

## Common Mistakes to Avoid

1. **Including YAML frontmatter in API calls**
   - ❌ Don't include `---\nname: foo\n---` in the `content` field
   - ✅ Use separate `name`, `category` parameters in API calls

2. **Using spaces in skill names**
   - ❌ `"Python Best Practices"`
   - ✅ `"python-best-practices"`

3. **Vague descriptions**
   - ❌ `"Useful commands"`
   - ✅ `"Deploy application to production. Use when user says: deploy, fazer deploy"`

4. **Missing critical rules**
   - ❌ No warnings about production/destructive operations
   - ✅ Use `## CRITICAL RULE` section with **NEVER**/**ALWAYS** statements

5. **Monolingual keywords**
   - ❌ Description only in English: `"Run tests"`
   - ✅ Bilingual: `"Run tests / Rodar testes. Use when user says: test, testar, run tests"`

6. **Over-permissive tools**
   - ❌ No `allowed-tools` restriction on automation skills
   - ✅ Restrict to necessary tools only: `["Bash", "Read"]`

7. **No success criteria**
   - ❌ Skill doesn't explain how to verify success
   - ✅ Clear, measurable success criteria listed

---

## Testing Your Skill

1. Create skill via DevManager API or UI
2. Sync to a **single test project** first
3. Start Claude Code session in that project
4. Trigger the skill (if user-invocable) or observe behavior (if background knowledge)
5. Verify Claude Code follows instructions correctly
6. Check for errors in skill parsing or execution
7. Once validated, sync to all projects
