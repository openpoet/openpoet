# OpenPoet safe rollout

Operational tooling to prepare and apply a release without compiling after the
running service has been stopped. The tool is **dry-run by default**. No
mutating command runs without `--execute`; `apply` also requires the exact
confirmation token generated by `prepare`.

`prepare` and `apply` go through the mandatory deploy gate
(`ops/deploy-gate/gate.sh`, see `docs/deploy-gate.md`): clean worktree and the
commit (HEAD for `prepare`, the manifest's `git_sha` for `apply`) on `main` and
on `origin/main`. There is no bypass here.

This tool does not replace human approval: restarting a production instance
still requires an explicit decision by its operator.

The `apply` step drives a macOS LaunchAgent (`launchctl bootout` /
`bootstrap`). Nothing in the tool assumes a particular installation: the
service binary, database, plist, launchd label and health URL are all passed as
flags.

## Flags that describe your installation

| Flag | Required for | Meaning |
| --- | --- | --- |
| `--live-binary` | `preflight`, `apply` | the binary the service runs |
| `--db` | `preflight`, `apply` | the service's SQLite database |
| `--plist` | `preflight`, `apply` | the LaunchAgent plist used to restart it |
| `--service-label` | `apply` | the LaunchAgent label (e.g. `com.example.openpoet`) |
| `--launch-domain` | `apply` | launchd domain; defaults to `gui/<uid>` |
| `--health-url` | `preflight`, `apply` | the service's version endpoint, e.g. `http://127.0.0.1:8080/api/version` |
| `--releases-dir` | `prepare` | defaults to `~/.openpoet-rollout/releases` |
| `--backup-dir` | `apply` | defaults to `~/.openpoet-rollout/backups` |

The examples below use shell variables for these values:

```bash
SERVICE_DIR=/opt/openpoet          # wherever your instance lives
HEALTH_URL=http://127.0.0.1:8080/api/version
```

## Flow

### 1. Inspect the plan

```bash
go run ./ops/safe-rollout prepare
go run ./ops/safe-rollout preflight
go run ./ops/safe-rollout apply
```

These commands write no files, run no tests or builds and never touch launchd.

### 2. Prepare a release

The worktree must be clean. Tests run before the artifact is created; the
build gets a `BuildVersion` equal to the release ID.

```bash
go run ./ops/safe-rollout prepare --execute \
  --repo "$PWD" \
  --releases-dir "$HOME/.openpoet-rollout/releases" \
  --relay-url "https://relay.example"
```

Outputs:

- an immutable directory `<releases-dir>/<release-id>/`;
- `openpoet` with its SHA-256 recorded;
- `manifest.json` with mode `0600`;
- a random confirmation token.

Build and tests happen while the service is still running. `prepare` refuses
a dirty tree so it never produces a binary that cannot be reproduced.

### 3. Read-only preflight

```bash
go run ./ops/safe-rollout preflight --execute \
  --manifest "$HOME/.openpoet-rollout/releases/<release>/manifest.json" \
  --live-binary "$SERVICE_DIR/openpoet" \
  --db "$SERVICE_DIR/openpoet.db" \
  --plist "$SERVICE_DIR/openpoet.plist" \
  --health-url "$HEALTH_URL"
```

Checks the artifact hash, the runtime files, `PRAGMA quick_check` and the
current `/api/version`. It changes nothing.

### 4. Authorized apply

Only after the operator explicitly approved the rollout:

```bash
go run ./ops/safe-rollout apply --execute \
  --confirm-token '<token-from-the-manifest>' \
  --manifest "$HOME/.openpoet-rollout/releases/<release>/manifest.json" \
  --live-binary "$SERVICE_DIR/openpoet" \
  --db "$SERVICE_DIR/openpoet.db" \
  --plist "$SERVICE_DIR/openpoet.plist" \
  --service-label com.example.openpoet \
  --health-url "$HEALTH_URL" \
  --backup-dir "$HOME/.openpoet-rollout/backups"
```

Actual order:

1. repeats the preflight;
2. takes a consistent snapshot with `VACUUM INTO` and validates the backup;
3. runs `launchctl bootout`, which sends SIGTERM to OpenPoet;
4. waits for `/api/version` to become unavailable, without `kill -9`;
5. keeps the previous binary and swaps in the candidate with an atomic rename;
6. migrates, in a single transaction, legacy MCP/custom tool configs to
   encrypted envelopes using `OPENPOET_ENCRYPT_KEY` (or the fallback the
   runtime already uses);
7. runs `launchctl bootstrap`;
8. requires three consecutive health checks reporting the release's exact
   version;
9. repeats `PRAGMA quick_check` on the live database.

If start or health fails after the secret migration, the previous binary and
the SQLite snapshot are restored before the LaunchAgent is reopened. The
migration output contains counts only.

### Offline preflight of the secret migration

The dedicated tool requires an explicit path and is dry-run by default. It
applies no schema migrations and never prints names, commands, env or
ciphertext.

```bash
go run ./cmd/openpoet-secret-migrate --db /path/to/openpoet.db

# Only after a backup and explicit approval:
OPENPOET_ENCRYPT_KEY='same-key-as-the-runtime' \
  go run ./cmd/openpoet-secret-migrate --db /path/to/openpoet.db --execute
```

## Intentional limits

- Two OpenPoet processes never share the SQLite database during apply.
- There is no `kill -9` fallback; a graceful stop that exceeds the timeout
  aborts.
- Rollback restores the database automatically only when this secret
  migration ran; other schema migrations still need their own N-1
  compatibility strategy.
- The operator must check that sessions are idle before apply. Auto-restore
  does not guarantee exactly-once for external actions in flight.
- The backup is consistent as of the `VACUUM INTO`; if the candidate fails
  after the secret migration, writes between the snapshot and the graceful
  stop are discarded by the restore. Drain activity before apply.
- Releases and backups live outside the repository by default.

## Tests

```bash
go test ./ops/safe-rollout
```

The tests only use temporary directories, a temporary SQLite database, local
HTTP and fake command runners. They never call launchd or reach a running
instance.
